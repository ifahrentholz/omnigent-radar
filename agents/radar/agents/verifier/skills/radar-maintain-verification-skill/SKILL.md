# Maintain a verification skill

A feature map rots the moment the app changes. This is the upkeep loop for a
skill generated by `verify-setup` (or any project-local verification skill
with a feature map). The unit of rigour is the feature, not every sentence:
cover every feature file from source and exercise every feature live, without
terminalising every bullet.

Adapted from open-pstack's `maintain-verification-skill` (see `UPSTREAM.md` in
the verifier's directory). The one structural difference: upstream fans out a
read-only subagent per feature, and a worker here cannot dispatch further. So
radar runs that **source wave** before it dispatches you — one `explorer` per
feature file, or per group of files when there are more than it may dispatch at
once — and your brief lists their report paths. You own everything after it.

## Outcomes

Pick one, and say which:

- **clean** — every feature got source and live coverage; nothing worth
  shipping. No diff.
- **changed** — proven doc, harness or map corrections, left uncommitted on
  the branch for `deliver` to ship as one PR.
- **blocked** — coverage could not finish or a proven fix could not be made
  safely. Say exactly what blocked it.

## Edit scope

Only edit the verification skill's own directory: its `SKILL.md`, `features/`,
and any harness scripts it owns. Never edit product code during a run. A
behaviour the map describes that the app no longer has is either doc drift
(fix the map) or a product regression (report it, do not paper over it in the
docs).

## Pass

0. **Locate the target.** The brief names it. If it does not, find the
   project-local skill whose body has launch and drive sections and a feature
   map (usually `.claude/skills/verify-*/`). Several candidates and none named
   → `blocked`, listing them; none at all → `blocked`, and name `verify-setup`
   in `next:` instead of inventing a target.

1. **Index hygiene.** Read the feature map README and list its sibling files.
   Fix missing, extra, duplicate or dead entries. Lightweight; no generated
   inventory.

2. **Take in the source wave.** Read every explorer report your brief lists.
   Each covers one feature file (or a named group) and returns a feature
   summary, the source entry points, likely drift with citations, and one
   live-verification recipe. A feature file without a report — the wave
   missed it, or hygiene just added it — you read from source yourself, the
   same way: from the user's entry point to the code that serves it. If the
   brief lists no reports at all, do the whole wave yourself, feature by
   feature, and say so in the report: it costs more of your context than the
   fan-out would have.

3. **Reconcile.** Every feature file has a summary. Merge overlapping recipes
   into as few app states as practical. Spot-check cited drift; do not
   re-prove clean claims. Sweep recent churn
   (`git log --since=<last map change> --stat`) for user-facing surfaces
   missing from the map — require a concrete source path before calling one
   missing.

4. **Live pass.** Required even when the source looks clean. You own all
   driving; follow the verification skill's own launch model — one long-lived
   instance driven serially for servers and UIs (in a terminal, so it keeps
   running between drives), or a fresh isolated session per drive for
   short-lived CLIs. The skill's Launch section decides, not this one.
   Exercise every feature at least once, and hold three invariants the whole
   pass, whatever the failure:

   1. **Never drive an instance you have not health-checked since it last did
      something surprising.** Doctor before the first drive, doctor on each
      fresh session where sessions are the unit, doctor again after any failed
      drive. Where doctor cannot see the failure (a wedged UI on a healthy
      process), reset to a known state or relaunch rather than hoping.
   2. **Evidence captured so far survives every cleanup**, checked at its
      location under `.omnigent/runs/<run-id>/evidence/`, not assumed.
   3. **Nothing a drive started outlives that drive's usefulness.**
      Failed-iteration residue is cleaned whether the session is stuck, exited
      or shared — for a shared instance, clean the residue, not the instance.
      Stop only what you started.

   A doctor failure caused by skill drift is drift: fix it under edit scope
   and retry once — restart whatever the fix invalidated, nothing more —
   before calling the pass `blocked`. A feature that cannot be reached is
   `unreachable` only with the concrete prerequisite (auth, entitlement, OS,
   external state) and the route attempted; if the map omits that
   prerequisite, that is drift. Any harness fix from triage gets re-driven
   live before it counts. Final teardown happens after the last drive of the
   run — including those re-proofs — so nothing outlives the run; the
   evidence stays.

5. **Triage.**
   - Wrong or missing user-POV description → doc drift; fix it.
   - Working behaviour the harness cannot drive → harness gap; fix it. A
     harness fix follows the same helpers rule as generation: scripts
     executable, invocation through the interpreter shown in the skill body.
   - App behaviour that is actually broken → product gap. Record it for the
     human with its evidence and keep it out of the diff.

6. **Hand over or stop.** For `changed`: re-read every file you changed, leave
   them uncommitted, and let `deliver` turn them into one PR. For `clean` or
   `blocked`: no diff; report the outcome and the coverage honestly.

Keep concise run notes — features covered, unreachable prerequisites,
confirmed drift, product gaps, outcome — in
`.omnigent/runs/<run-id>/report.md`. They are gitignored and never committed.
Then return exactly the block your brief asks for.
